## Owner-approved customer WeChat policy — retain across handoffs

1. After language selection and a valid manager/boss invitation QR, ask the customer for their **WeChat ID**. Offer **Save and continue** and **Skip for now**. Account settings must permit adding or editing it later.
2. No WeChat ID: browsing venues, availability, staff profiles/photos and package information stays available. Viewing existing bookings, history and notifications, changing language, and editing contact details stays available.
3. No WeChat ID: block ALL six owner-approved categories:
   - New staff bookings.
   - Package A/B reservations.
   - Table/private-room reservations, wherever these are actually offered.
   - Requests to change an existing booking/reservation (date, time, staff, package, etc.).
   - Cancellation requests for bookings, packages and reservations. The owner explicitly approved this inclusion with no omissions.
   - Manager-help/conflict-resolution requests associated with bookings or services, wherever offered.
4. Attempts must display a prominent localized toast explaining that the WeChat ID lets managers contact the customer about the request, with an **Add WeChat ID** action. Check both navigation and submission; do not rely only on disabled buttons.
5. **Critical follow-up approved by the owner:** customers MUST cancel or complete all outstanding bookings, packages, table/room reservations and other relevant services before deleting their WeChat ID. If existing backend logic does not already enforce this, add the guard in the appropriate future implementation step. A pending cancellation request is NOT a cancelled booking. Retain the ID until cancellation has actually been approved, or service/booking completion has been recorded. One closed item must not unlock removal while another item remains open. Whitespace/blank-save, explicit Remove and any alternate clearing path must share the same guard. Production must enforce the guard atomically on the server, including races with new bookings; frontend-only checks are insufficient.
6. The ID is a contact identifier, not verified WeChat ownership or authentication. Do not describe this preview's format check as identity verification.

### Preview implementation and limits

`customer-contact.js` centralizes contact gates, toast, optional onboarding, booking examples, manager review and ID removal guards. Contact details and synthetic records live in page memory and reset on reload; they are not sent to an API or saved to GitHub. The browser's preview role picker switches among all roles for review; it is not production authorization. An existing confirmed sample booking intentionally lets reviewers test the removal guard. Additional demo requests can be submitted for ordinary service and both package types; manager screens allow preview confirmation, cancellation approval and completion. Cancellation/changes remain requests until manager approval. This does not define payment, price, refund or charge behavior. No actual customer table/room reservation flow has been added: the same policy must be applied when that flow is implemented.

## Manager WeChat shortcut — desired outcome and unresolved platform constraint

The owner wants the equivalent of `t.me/username`: open WeChat externally with the specific customer's conversation ready, from any manager screen showing that customer. This is an efficiency goal; the owner does not require an unsupported hack.

Research on 24 October 2026 did not establish an officially supported personal-account chat URL that can be derived from a WeChat ID. WeChat Mini Program URL Scheme/URL Link APIs are a different capability; do not misrepresent them as personal-chat links. Do not fabricate `weixin://...chat?<id>` or a personal contact QR from a plain ID. Telegram's documented `openLink` opens an external browser and is not evidence that a custom WeChat scheme works on every Telegram client.

Implemented: consistent **Contact on WeChat** access in manager table/room, booking and package detail contexts, including related service-review screens; contact screen with actual session ID and honest manual fallback instructions. Selecting Contact on WeChat also attempts to copy the ID in that same user gesture, reducing one step; the contact screen retains an explicit Copy ID retry/fallback. Clipboard failure is reported honestly. If no ID exists, show that it has not been supplied. No external WeChat conversation is opened or message sent. The direct-chat shortcut remains **BLOCKED / NOT VERIFIED**, not completed. A future thread may replace the fallback only after documenting a supported target-specific mechanism and testing it inside Telegram on actual Android/iOS devices. A genuine customer-supplied WeChat profile QR or other integration is a separate proposed option, not an approved new required onboarding field.

Primary references consulted: https://core.telegram.org/bots/webapps (openLink/openTelegramLink), https://developers.weixin.qq.com/miniprogram/dev/framework/open-ability/url-scheme.html (official WeChat page was inaccessible to the research tool; do not claim its contents were verified). Do not infer a personal-chat link from unofficial examples.

## 24 October 2026 — shared UI, reservations and staff dashboard

Owner requested this complete preview refinement; implemented in `experience.js`, `experience.css`, and `experience-locales.js`, alongside extensions to `customer-contact.js`.

- Bottom navigation now uses representative inline SVG icons, a dollar sign for finance, and a circular account photo. Empty profiles use a deterministic, mirrored 8×8 Blockies-style identicon seeded by the display identity and preview role, in the app's red/navy/white palette. This is a themed identicon, not a wallet identity or authentication feature. Staff have circular photos beside their nickname. Back controls are high-contrast arrow icons with translated accessible labels. Headers center the logo and right-align nickname (otherwise Telegram username, or `@yourusername` in the demo), then venue and role. Telegram metadata is display-only and is not treated as verified backend identity.
- All application validation/error messages now use the shared ten-second toast, including QR, payment evidence and profile-image errors. Active toasts translate when the language changes.
- Customer venue tiles include explicitly fictional sample addresses. Venue pages offer room/table reservation buttons plus separate price/inclusion sheets. Four AI-generated views of a fictional karaoke lounge support thumbnails and an enlarged room viewer. Sample room MYR 480 / up to 12 guests; table MYR 180 / up to 6 guests. Drinks/facilities/prices/capacities are sample content, NOT approved operational rates or actual venue promises.
- Sheets slide up for entry, fade between details/form/review, and slide down into staff selection. The form has guest count, a native calendar picker and custom 12-hour, 60-minute and AM/PM scroll wheels. Wheel selections align to the center, support touch scrolling and keyboard input, and convert noon/midnight correctly. Animation respects reduced motion.
- Submit Reservation opens a review sheet. Book Staff holds the draft while showing the staff gallery; zero, one or multiple staff may be selected. The fixed-width reservation action remains above navigation throughout customer subpages and also appears inside the staff photo lightbox. Editing preserves selections; Start over discards only the unsent draft. A held draft cannot silently move to another venue/type. Submission creates only an in-memory Pending Review record visible to managers. It reserves no real inventory, sends no real notification and charges no money.
- The confirmation displays sample staff rates of MYR 100/hour each and explains manager-confirmed billable time. Do NOT silently implement automatic whole-hour rounding: frozen FIN-CL.1 uses manager-selected billable minutes and exact per-component monetary rules. The owner's phrase “hourly block pricing” is represented by hourly rate disclosure; any different billing rule requires explicit backend/spec reconciliation. Room/table prices in this preview are not new backend financial policies.
- Customer Bookings retains in-place Active / History tabs. Status tags cover Pending Review, Confirmed, Amendment Review Pending, Amendment Confirmed and Rejected / Cancelled. Recent rejected/cancelled examples can remain visible in Active for outcome visibility, and also in History; they do not block contact removal. Completed records move to History. Reservation amendments support guest count and date/time; cancellation stays a manager-review request. This display behavior does not authorize automatic cancellation or refunds.
- Notifications replaces Updates. An unread badge counts only the last ten days; older items are omitted. Open a notification to mark it read, or use Mark all as read. Demo manager booking/amendment/cancellation approvals and rejections generate corresponding in-memory notices. There is no Telegram message delivery or server-side retention implementation.
- Account supports local profile-photo upload/removal (center-cropped, resized to 512px), nickname, WeChat ID and optional WhatsApp number; blank contact fields say they disable that method. The prior owner-approved WeChat gate remains in force: WhatsApp alone does not unlock booking actions. Clearing WeChat still requires all open bookings/reservations/packages/services to be cancelled or completed; all clearing paths use the shared guard. Contact details/photos are page-session memory only. Browser-native calendar/file facilities follow the user's device settings; all app-controlled text has four locale entries.
- Staff dashboard has Bookings & Packages, Finance Quickview (Earnings Accrued / Outstanding Loan), Leaderboard and Leave Schedule. Clock Out submits an end-time report for manager acknowledgement, adds an Actions item/counter, prevents duplicate reports and updates the staff preview after acknowledgement. This does not calculate pay, post financial entries, automatically release floor assignments, settle a package or bypass normal manager billing review.
- Leaderboard uses seven fictional profiles sorted by example earnings, circular photos and nicknames, right-aligned earnings/table hours/package A/package B counts, gold/silver/bronze borders and a crown for first place. Month selection covers this month and six prior months, with an Accrued/Finalized pay selector; current-month finalized figures are unavailable. All example figures are synthetic; this explicitly requested UI does not amend backend peer-finance access policy. Outstanding Loan is the requested dashboard label, not a reclassification of all existing Outstanding balances. Leave counts/dates are also examples.

Additional validation: `node tests/experience.cjs` covers four locales, shared chrome/identicons, ten-second errors, ten-day notification cutoff/read state, WeChat reservation gating, guest/date/time handling, midnight/noon, zero/multiple staff, held draft/dock, manager approval/amendments, profile clearing guards, Clock Out acknowledgement and leaderboard filters. Existing gallery, floor/invitation and customer-contact suites are retained. Browser checks at 360px covered reservation → staff selection → lightbox → confirmation → submission → manager approval → notification; optional contact/photo profile changes, centered wheels, dashboard width and Clock Out Actions. These are browser/demo checks, not actual Telegram/device QA or production integration.
